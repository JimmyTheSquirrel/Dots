## Starship Prompt

## btop

**Module:** `Modules/Shell/btop.nix`
**Used on:** all four hosts (Sisyphus, Kit-Kat, Asgard, Apollo)

Home Manager `programs.btop` — the package is installed by this module, **not** by `base.nix`.

### Transparency

`theme_background = false` is the knob that does it: btop then skips painting `main_bg` and the terminal background shows through (kitty runs at `background_opacity 0.70`).

btop emits **no cell-background SGR sequences at all** in normal operation — `meter_bg` colours the *glyph* of the unfilled meter segment, not the cell behind it. So nothing punches an opaque rectangle through the transparency. Only the menu selection and the process pause/follow banners use a real background colour.

### Theme

One theme, named `dots`, generated by `mkTheme` in `Modules/Shell/btop.nix`. That generator is instantiated twice from a single mapping so the two can't drift:

| Instance | Colours | Path | Written by |
|----------|---------|------|-----------|
| fallback | literal hex (tonal-spot dark, teal source) | `~/.config/btop/themes/dots.theme` | HM activation `btopTheme` |
| live | matugen template tokens | same path | matugen, on every wallpaper change |

The template is exported as `flake.lib.btop.matugenTemplate` and consumed by `Modules/Desktop/skwd.nix`, which installs it into skwd's matugen template dir and registers the `btop` integration.

**The theme file is deliberately not a home-manager symlink.** matugen has to overwrite that exact path, and store symlinks are read-only. The activation script seeds it as a plain 0644 file and refreshes it only when the file is missing *or* still byte-identical to the seed it installed last time (tracked via `themes/.dots.seed`). Once matugen has taken ownership, editing the fallback palette in Nix no longer clobbers the live wallpaper colours — so if you change `fallbackPalette` and see no effect, that's why; it only ever shows before the first wallpaper change, or on hosts with no skwd (Asgard, Apollo).

**Editing `mkTheme` and rebuilding is not enough once matugen owns the file.** A rebuild updates the *template*, but nothing re-renders it until the next wallpaper change — the live theme keeps whatever mapping was current when matugen last ran. Check which version you're actually looking at before concluding a change didn't work:

```bash
grep -E 'cpu_box|div_line' ~/.config/btop/themes/dots.theme   # live colours
cmp -s ~/.config/btop/themes/dots.theme ~/.config/btop/themes/.dots.seed \
  && echo pristine || echo matugen-owned
```

Force a re-render without picking a new wallpaper by re-applying the current one — this runs every integration, not just btop's:

```bash
skwd wallpaper set "$(jq -r .path ~/.cache/skwd-wall/last-wallpaper.json)"
```

That re-renders the template and fires the reload hook, so an open btop repaints itself — no restart needed.

### Live reload — `SIGUSR2`

btop has no IPC socket, but it does have a hot-reload signal, and it covers the theme. `SIGUSR2` (identical to pressing `Ctrl+R`) sets `Global::reload_conf`, and the main loop then runs `init_config()` → `Theme::updateThemes()` → `Theme::setTheme()`. `setTheme()` calls `loadFile(theme_path)`, so the theme is re-read **from disk** rather than from a cache — a running btop repaints in the new palette with no restart and no lost state (`src/btop.cpp:1139`, `src/btop_theme.cpp:445`).

`btop-reload-theme` (a `writeShellScriptBin` in `Modules/Shell/btop.nix`) wraps `pkill -USR2 -x btop` and is registered as the skwd `btop` integration's reload command, so a wallpaper change repaints any open btop instantly.

- `-x btop` is correct here — nixpkgs does **not** wrap btop, so its process name is exactly `btop` (unlike swaybg, which is `.swaybg-wrapped`; see `Claude/skwd-wall.md`).
- `|| true` matters: `pkill` exits 1 when no btop is running, which skwd-daemon would otherwise log as a failed reload on every wallpaper change.

### Colour and symbol choices

**Borders** are uniform `on_surface_variant` — close to text brightness — with dividers one step down at `outline`. Both `outline` and `outline_variant` were tried for the borders first and read as washed-out over a wallpaper. With nothing behind them the borders are the only thing carrying the layout, so they can't be a subtle accent the way they could over a solid background.

**Each meter gets its own hue** so the four mem bars stay distinguishable: used → primary→error, available → tertiary, cached → secondary, free → neutral. Download rides the primary ramp, upload the tertiary one.

**`graph_symbol = "braille"` everywhere**, with the per-box overrides left unset so they inherit it. `graph_symbol_mem` and `graph_symbol_proc` were briefly set to `"block"` on the theory that meters read better as solid bars; they render as chunky opaque slabs that look nothing like the rest of the UI. Braille has 4x the horizontal resolution and matches the CPU/net graphs — switching back cut block glyphs in a rendered frame from 1189 to 5 (the remainder is the scrollbar, not graphs).

### Every gradient floor must stay bright — don't reintroduce container tones

The first version of this theme used Material You *container* colours (`primary_container` `#00504e`, `tertiary_container` `#324863`, `outline_variant` `#3f4948`) as the `_start` of each ramp, on the reasoning that an idle system should render quietly. **That was wrong for a transparent terminal** and it looked broken in practice: per-core `%` values, the CPU graph, the core mini-graphs and most of the process list disappeared into the wallpaper, because btop interpolates `start→mid→end` by value and an idle machine sits at `start`.

There is no background to guarantee contrast against — that's the whole point of `theme_background = false` — so the wallpaper's luminance under any given cell is unknowable. Bright colours read over a light wallpaper *and* a dark one; dark colours only work against a background we control.

Measured across the distinct foreground colours in a rendered btop frame:

| Version | below luma 150 |
|---------|----------------|
| container floors (v1) | 96 of 187 |
| current | 2 of 78 |

Both survivors are deliberate: `outline` `#889392` (dividers and `inactive_fg`) and `outline_variant` `#3f4948` (the unfilled meter track, which is meant to recede).

If you ever want the "quiet at idle" look back, the only safe way to get it is a background btop controls — i.e. raise kitty's `background_opacity`, not lower the ramp floors.

`proc_gradient` is off for the same reason: it fades process rows toward `inactive_fg` going down the list, which is handsome on a solid dark background and unreadable over a wallpaper.

### In-app changes don't persist

`btop.conf` is a read-only store symlink, so btop's own "save on exit" is a no-op. Sorting, filters, and preset changes made with the keyboard last only for that session — change them in `Modules/Shell/btop.nix` to make them stick.

blanks `FZF_DEFAULT_OPTS` for that one command. It ships no cheats of its own. Every entry

offer commands that could not run there.

`deploy-tools.nix` is imported on **Sisyphus only**. It installs the commands below and
`~/.config/navi/cheats/dots.cheat` (navi reads every `*.cheat` under its cheats path):
- `system-rebuild`: interactive or CLI rebuild/deploy menu. Its third action is **Build**
  (`nixos-rebuild build`, no sudo); it was mislabelled "Test" before. `--build` and the
  old `--test` both mean build.
- `git-sync`: stash, pull --rebase, push.
- `nix-gc`: the do-it-now cleanup: `nix-collect-garbage -d` (**every** old generation),
  `nix-store --optimise`, and `docker system prune` where Docker exists. The routine
  version is automatic: weekly nix.gc/optimise and a journald cap in `base.nix`, and
  Docker autoPrune in `wolf.nix`.
- `apollo-iso`, `apollo-key`, `apollo-connect`, `apollo-deploy`: see `Claude/deploy.md`.
  `apollo-connect` and `apollo-deploy` share one live-node lookup, `apollo-resolve`,
  which is their runtime input and not on PATH.
- `sops ~/Dots/Secrets/secrets.yaml`, `ssh asgard`, `ssh kitkat@kit-kat`: cheats only.

Each command is a `pkgs.writeShellApplication` whose body is
`Resources/Scripts/<name>.sh`, plain bash read with `builtins.readFile`. **shellcheck runs
at build time**, so a finding fails the rebuild. You can also run it directly:
`shellcheck --shell=bash Resources/Scripts/*.sh`. The bodies set no shell options because
`writeShellApplication` already sets errexit/nounset/pipefail. `runtimeInputs` are
*prepended* to `PATH`, so `sudo` (`/run/wrappers/bin`) and the system's own
`nix`/`nixos-rebuild`/`tailscale` still resolve.

These were once duplicated as zsh functions in `Resources/Zsh-Scripts/zsh-helpers.sh`, which caused the two copies to drift (navi ran a stale menu without Asgard). That file was deleted (July 2026). Do not reintroduce shell-function copies; edit `Resources/Scripts/` instead.

## Audio

**Module:** `Modules/Core/audio.nix`: a minimal PipeWire setup. It has ALSA, PulseAudio compat via pipewire-pulse (the PulseAudio daemon stays off, the default), and rtkit for realtime scheduling. **WirePlumber's Bluetooth (bluez) monitor is on.** Until 2026-10-03 a `10-disable-bluez` profile turned it off on every desktop. Paired Bluetooth headphones then connected but never appeared as a sink. That was never intended.

**Hardware:** Corsair Virtuoso XT Wireless (USB dongle, default sink/source). USB autosuspend is NOT an issue — the receiver is hardlocked to `power/control = on` by the kernel.

**WirePlumber startup warnings** — `wp_event_dispatcher_unregister_hook: assertion ... failed` appears on every boot. Known WirePlumber 0.5.x bug, harmless, audio works fine.

**Every noctalia host (Sisyphus, Kit-Kat, Apollo) has a second sink, `spotify_tap`** — a loopback that Spotify plays into and
which forwards to the default sink, so noctalia's bar visualizer can tap Spotify alone instead of
the speaker monitor. Defined in `Modules/Desktop/noctalia.nix`, not `audio.nix`, because it exists purely
for that widget. If Spotify has no sound, check that loopback before anything else:
`pw-link -l | grep -A2 '^spotify:output'`. Full explanation in `Claude/noctalia.md`.

**Stream routing rules live in PipeWire's configs, not WirePlumber's.** `pulse.rules`
(`pipewire-pulse.conf.d`) for PulseAudio clients, `stream.rules` (`client.conf.d`) for native
libpipewire clients. WirePlumber's same-named `stream.rules` only drives its save/restore
bookkeeping and will not move a stream.

### Audio routing toolkit — `qpwgraph`, `pwvucontrol`, `coppwr` (`Modules/Core/audio.nix`)

Installed on all hosts for building and debugging PipeWire graphs by hand.

- **qpwgraph** — visual patchbay. Only *connects* existing ports; it cannot create a virtual
  device. Mint one first with `pw-loopback`, then wire it up:
  ```bash
  pw-loopback -n mic_mix --capture-props='media.class=Audio/Sink' \
              --playback-props='media.class=Audio/Source/Virtual'
  ```
  Saved patchbay files land in `~/.config/rncbc.org` — imperative state, so treat qpwgraph as a
  prototyping tool and commit the working graph to Nix afterwards.
- **pwvucontrol** — per-app volume and routing without the graph (pavucontrol's successor).
- **coppwr** — raw node properties. Use it when a `pulse.rules` / `stream.rules` match isn't
  firing and you need the exact props a node was created with.

> A previous attempt to declare a "Mic + Music" virtual source in Nix (`Modules/mic-mix.nix`)
> was **removed 2026-08-09**. Its `mic_mix` loopback never negotiated a format — the capture side
> resolved to DSP with no channel count while the playback side wanted raw 2ch F32P, so
> `mic_music` failed to start with `-95 Operation not supported` on a permanent retry loop that
> filled ~35% of the journal. Don't re-add that module shape without fixing the format
> negotiation first. See "Measuring this correctly" below before trusting any test of a rebuild.

#### Measuring a PipeWire graph correctly — the trap that invalidated a whole test round

**`pw-record --target <sink-id>` does NOT capture that sink's monitor.** It silently falls back
to the *default source*, so you sit there measuring the hardware microphone and drawing
confident conclusions about a chain you never recorded. It produced a completely wrong reading
that `wpctl set-mute` doesn't work on loopback nodes — it works fine.

Always pass the capture-sink property, and **verify the link before trusting a number**:

```bash
pw-record -P 'stream.capture.sink=true' --target mic_mix --channels=2 out.wav &
sleep 2; pw-link -l | grep -A2 '^pw-record:input_FL'    # MUST show mic_mix:monitor_FL
nix shell nixpkgs#sox -c sox out.wav -n stat            # muted ⇒ Maximum amplitude 0.000000
```

Two more measurement traps from the same session:
- **gzip size is not an amplitude proxy.** Mic noise compresses badly, so "silent" and "loud"
  came out within 20% of each other. Use `sox -n stat`; digital silence is unambiguous (0.000000).
- **`pw-record -q` takes an argument** (resampler quality 0-15), so `-q --channels=2` eats the
  next flag and you get a 44-byte header-only WAV. A 44-byte output means the arguments were
  wrong, not that the source was silent.

And when killing test rigs: `pkill -f pw-loopback` matches **your own shell** if the command line
that started it is still in scope — it will kill the shell running the pkill. Kill by PID.

### Known audio cutout causes and fixes

**Steam/CS2 — old libpipewire causing mid-session dropouts:**
Steam bundles its own old `libpipewire-0.3.so` (protocol v4 vs system's 1.4.9). Games using it directly (CS2) periodically lose sync with the PipeWire server, producing `mod.client-node: detected old client version 4` in the PipeWire log and audio cutting out.
Fix (already in `steam.nix`): add `pipewire` to `extraLibraries` alongside `libpulseaudio`.

**Discord/Vesktop — passing Chromium flags at all:**
**`~/.config/vesktop/argv.json` is NOT read by Vesktop** — the string `argv.json` does not occur anywhere in its `app.asar`. A `--enable-features=WebRTCPipeWireCapturer` entry lived there for a long time and never applied. Don't reintroduce that pattern.

Flags must reach Electron on the real command line. The nixpkgs wrapper ends in `exec electron app.asar … "$@"`, so `discord.nix` wraps the package with `symlinkJoin` + `wrapProgram --add-flags`.

Only `--disable-features` is safe to add that way. Vesktop calls `appendSwitch("enable-features", …)` internally, and the nixpkgs wrapper already passes `--enable-features=WaylandWindowDecorations` under `NIXOS_OZONE_WL` — duplicate `--enable-features` on one command line is last-wins, so a second one silently drops Wayland decorations.

Verify a flag actually landed (never assume — `argv.json` looked fine on disk for months):
```bash
tr '\0' '\n' < /proc/$(pgrep -f vesktop | head -1)/cmdline | grep features
```
Note `pgrep -x vesktop` matches nothing — nixpkgs wraps it and `comm` is `electron`. Same trap as `.swaybg-wrapped`.

**Discord noise suppression/echo cancellation** — these run as a separate processing thread that can disconnect mid-call. If dropouts persist after the above fix, turn them off in Discord Settings → Voice & Video. Not configurable declaratively (stored per-account server-side).

### Mic volume drops on its own (WebRTC AGC)

**Symptom:** input volume ratchets *down* in small steps and never recovers — e.g. `1.00 → 0.94 → 0.88` within 75s. Because Chromium's AGC rewrites the **hardware** source volume via the Pulse API (which PipeWire honours) rather than applying gain in software, the damage is system-wide: every other app gets the reduced mic too.

**Fix (in `discord.nix`):** `--disable-features=WebRtcAllowInputVolumeAdjustment`, passed by the `wrapProgram` wrapper (not `vesktop/argv.json`, which Vesktop never reads, see above). CLI equivalent of `chrome://flags#enable-webrtc-allow-input-volume-adjustment` → Disabled. Also turn off Discord → Settings → Voice & Video → **Automatic Gain Control** (server-side, not declarative).

**Diagnosing which app:** monotonic downward steps = WebRTC AGC, so suspect Electron/Chromium clients first. `cs2` and `Noctalia Spectrum` also hold capture streams on Sisyphus but do their gain in software. To confirm, poll `wpctl get-volume @DEFAULT_AUDIO_SOURCE@` in a loop and log changes against the apps listed by `pw-dump | grep -B40 '"media.class": "Stream/Input/Audio"'`.

**Steam Linux Runtime (pressure-vessel) — old libpipewire causing system-wide dropouts:**
Games running in the Steam Linux Runtime container (e.g. CS2) use their own bundled old `libpipewire-0.3` (protocol v4). Pressure-vessel overrides `LD_LIBRARY_PATH` entirely, so the `extraLibraries` fix in `steam.nix` does NOT reach these games. CS2 connecting with the old protocol desynchs from the PipeWire server and causes dropouts for all other audio clients (Spotify, Discord, everything).
Fix (already in `base.nix`): `environment.sessionVariables.SDL_AUDIODRIVER = "pulseaudio"` — forces all SDL apps to use the PulseAudio backend (routes through pipewire-pulse) instead of connecting to PipeWire directly with the old library. Propagates into pressure-vessel via Steam's inherited environment.

## Discord

**Module:** `Modules/Apps/discord.nix`

Uses Vesktop (Discord + Vencord) instead of regular Discord:
- Better Wayland/Linux support
- Native transparency (`transparent = true`) plus a quickCss that forces
  transparent backgrounds with `!important`
- Chromium switches via a `wrapProgram` wrapper

**`argv.json` is never read.** Vesktop does not contain the string anywhere in
`app.asar`, so the `--enable-features=WebRTCPipeWireCapturer` it used to carry
was never applied despite being documented as the voice-dropout fix. Flags go
through the wrapper instead, and only `--disable-features` is safe to add — Vesktop
already appends its own `--enable-features`, and duplicates are last-wins, so a
second one silently drops Wayland decorations.

### Two settings files, and which one matters

| file | owner | controls |
|---|---|---|
| `~/.config/vesktop/settings.json` | Nix (`xdg.configFile`) | **Vesktop/Electron window** — `transparent`, `frameless`, `arRPC` |
| `~/.config/vesktop/settings/settings.json` | Vencord, runtime | **`enabledThemes`, `useQuickCss`**, plugins |

`enabledThemes` in the *first* file is a no-op — it was set there until
2026-09-15 and never did anything. It cannot be an `xdg.configFile` either, since
Vencord rewrites it on every settings change, so `Modules/Apps/discord.nix` patches
just its keys from an activation script (same jq-upsert pattern as
`Modules/Desktop/skwd.nix`). Note `quickCss.css` is **not a theme** — it is the Quick CSS
box, gated by `useQuickCss`; listing it under `enabledThemes` never meant anything.

### Colours follow the wallpaper

skwd renders `~/.config/vesktop/themes/matugen.theme.css` — **custom properties
only**, no selectors — and quickCss consumes them with fallbacks to the old flat
black. Vencord hot-reloads the file, so no reload command is needed.

**Never enable a full Discord theme alongside this.** noctalia's community
`discord` template (a 20 KB opaque redesign) was enabled on 2026-09-15 and made
the transparent client glitch badly. Details in `Claude/skwd-wall.md`.

**If Discord is transparent but untinted after a rebuild**, check
`enabledThemes` in `vesktop/settings/settings.json` before suspecting the render
pipeline. Vencord keeps settings in memory and writes the whole file back on any
settings change, so a write landing after the activation script clobbers the
patch. Reload Discord with Ctrl+R; it is self-correcting once Vencord holds the
value. The quickCss fallbacks mean the failure looks like "colours never
applied", not like a broken client.

**Cache clearing:** The module clears Vesktop's Chromium caches (`Cache`, `Code Cache`, `GPUCache`) only when the Vesktop package changes. The store path is the key, so it also changes when the Electron underneath is updated. Electron caches are not guaranteed readable across builds; this was the original "EPIPE errors" fix. The stamp is `~/.config/vesktop/.dots-vesktop-build`; delete it to force a clear on the next switch. It used to wipe them on *every* switch, which made every next launch cache-cold and deleted files from under a running Vesktop. Login session is preserved either way.

## Thunar

**Thunar is the file manager.** Dolphin was trialled on 2026-09-26 and rejected
the same day — see `Claude/dolphin.md`. Don't re-propose it.

Stock GTK look, on purpose — no theme swap, no icon pack, no wallpaper colours.
A full adw-gtk3-dark + Papirus + matugen setup was built on 2026-09-25 and
**rejected on taste**; it was reverted the same day, `Modules/gtk.nix` deleted,
and the skwd gtk3/gtk4 integrations removed. Don't rebuild it.

### Transparency comes from the niri rule — and the app-id has two spellings

`Modules/Desktop/niri.nix` carries `match app-id="^[Tt]hunar$" opacity 0.90`,
and it works. **Both spellings are required:** GTK takes the app-id from
prgname, so the autostarted `Thunar --daemon` produces `Thunar` while
`.../bin/thunar` (Mod+E) produces `thunar`, and niri matches case-sensitively.
The old `^thunar$` never matched a daemon-served window, so whether Thunar was
see-through depended on who opened it.

⚠️ **Don't conclude "the rule does nothing" from one pixel sample.** Thunar's
background is very dark (#1d1d20 ≈ 29,29,32), so at 0.90 the wallpaper
contributes 10% — over a dark wallpaper the composite is numerically identical
to an opaque window. That produced a confident and wrong diagnosis on
2026-09-25. Sample where the wallpaper is bright and compare against the
client's own buffer colour: verified at 34–42 per channel against a 29 buffer,
i.e. exactly `0.9*29 + 0.1*wallpaper`.

Technique: `niri msg action screenshot-window` renders through niri, so its
alpha *includes* the window rule; a full-screen `grim` capture shows the final
composite; read pixels with `magick shot.png -format "%[pixel:p{x,y}]" info:`
(ImageMagick is not on `PATH` — use the store path).

niri's opacity is **uniform**: it fades text along with the background, which is
why this reads as "dim" rather than "glassy". Only client-side alpha (a
`gtk.css`) fades the background alone — that route was built and rejected on
taste (above). If it is ever rebuilt it can be colour-free:
`window, .background { background-color: alpha(@theme_bg_color, 0.90); }`
keeps the stock look and adds nothing but transparency.

⚠️ `environment.etc."gtk-3.0/settings.ini"` in `Modules/Desktop/thunar.nix` **is never
read by GTK** — GTK reads `$XDG_CONFIG_DIRS/gtk-3.0/settings.ini` (`/etc/xdg/…`)
and a build-time sysconfdir that on NixOS is a store path, never `/etc/gtk-3.0`.
The block is inert; the live look comes from `~/.config/gtk-3.0/settings.ini`,
which is imperative leftover state.

## Media Viewers

Both installed via `base.nix`:

**Video:** `mpv` — handles all formats including `.MOV`/QuickTime. Keyboard-driven, minimal.

**Images:** `imv` — Wayland-native image viewer. Arrow keys to browse, `q` to quit.

**Default app associations:** Declared via `xdg.mimeApps` in `base.nix`. Covers all common video MIME types → `mpv.desktop` and image MIME types → `imv.desktop`. Changes take effect after log out/in (session must refresh `XDG_DATA_DIRS`).
