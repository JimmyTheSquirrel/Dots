# Cult of the Lamb lag spikes — 2026-10-09 session

Captured live while the session was running (19:17–20:36). Sisyphus → Eclipse over Wolf.
**Verdict: 100 Mbps of bursty UDP over Eclipse's own −67 dBm Wi-Fi radio.**
Not Proton, not the GPU, not the Pi — **and not the extender, which was not in the path at all.**

## ⭐ The path is not what anyone assumed

Eclipse has **both NICs up on the same subnet**, and the Wi-Fi one wins:

| iface | address | route | rx during the stream |
|---|---|---|---|
| `eth0` | 192.168.0.182 | wired → RP-BE58 extender | **0 Mbps** |
| `wlan0` | 192.168.0.183 | direct to "Kandy Cane", 5 GHz ch36 | **101 Mbps** |

```
ip route get 192.168.0.13   -> 192.168.0.13 dev wlan0 src 192.168.0.183
ip route get 192.168.0.226  -> 192.168.0.226 dev wlan0 src 192.168.0.183
default via 192.168.0.1 dev eth0
default via 192.168.0.1 dev wlan0  metric -3073     <- wins
```

connman has **both** `Wired` (`*AO`) and `Kandy Cane` (`*AR`) with `AutoConnect=true`.
`wlan0` had been associated **18,053 s ≈ 5 h** on a box up **4 days** — so it joined around
**15:35 on 2026-10-09**, hours before the session, and silently took the default route.
`eth0` is fine throughout (`carrier=1`, 42 GB lifetime rx); it is simply unused.

**Consequences:** every documented extender tuning is bypassed, and *every measurement through
the dashboard is of the Wi-Fi radio, not the extender.*

`wlan0` link, measured: **signal −67 dBm**, rx PHY 292.5 Mbit/s, tx PHY 195.0 Mbit/s,
`tx failed: 52`. −67 dBm is exactly the weak corner predicted in
`eclipse-extender-bridge-bottleneck` ("that corner of the house at −68 dBm").

## What was asked for

Eclipse `Moonlight.conf`:
`width=3840 height=2160 fps=60 bitrate=100000 packetsize=0 videodec=0 vsync=true framepacing=false hdr=false`

Measured on the wire from Sisyphus (`enp9s0`, 10 s sample):
**101 Mbps, 9265 pps, 1367 B avg packet** — Wolf delivered the full 100 Mbps as asked.

## What arrived

Session 1:04:08 long, 229,149 frames, 59.6 fps avg — the encoder *was* producing a clean 60 fps.

| Counter | Value |
|---|---|
| Frames lost | **16,283 (7.1 % of all frames)** |
| Audio drop events | 3,467 |
| `Unrecoverable frame` | 16,212 |
| Failed FEC blocks | 19,671 |
| …of those with **zero** parity received | **16,256 (83 %)** |
| Wolf `skipping FEC` events | 27,628 |
| Distinct freeze events | 1,090 (437 during gameplay) |
| Worst single freeze | 46 consecutive IDR waits ≈ **0.77 s frozen** |
| Worst 5-min window | 109 freezes (≈ 20:07–20:12) |

437 freezes across ~52 min of gameplay = **a visible stutter every ~7 s**, in clusters.

## The mechanism

1. At 100 Mbps / 4K60, a frame is ~294 packets split into **3 FEC blocks**.
2. Moonlight's FEC block index is 8-bit, so **a block over 255 packets cannot carry FEC**. Wolf
   logs `Size of frame too large, N packets is bigger than the max (255); skipping FEC` and ships
   the frame **unprotected** — 27,628 times. Observed oversized blocks: median 308, max 622.
3. 101 Mbps of **bursty** UDP over a −67 dBm Wi-Fi link is roughly 60 % airtime before retries.
   Frame bursts exceed instantaneous capacity and the queues shed packets. ICMP at ~1 Mbps sails
   through untouched, which is why latency probes look innocent — **the loss only hits the peaks.**
4. A single lost packet in an unprotected frame is fatal → `Unrecoverable frame`. 83 % of failures
   had **no parity at all**, so there was nothing to recover from.
5. Every dependent frame is then discarded → `Waiting for IDR frame` 40-46 times in a row → the
   picture freezes until a keyframe arrives. **That is the lag spike.**

Verbatim, the worst cluster:
```

00:51:14 - Unrecoverable frame 182922 (block 1 of 3): 98+12=119 received < 108 needed
00:51:14 - Network dropped 1 frame (frame 182922)
00:51:14 - Waiting for IDR frame
00:51:14 - IDR frame request sent
00:51:04 - Network dropped 36 frames (frames 182292 to 182327)
```

## Latency — and why it misleads here

All from Sisyphus, wired, 1400 B payload, ~1 Mbps probe rate, **with the stream running**:

| Target | min | avg | max | mdev |
|---|---|---|---|---|
| gateway `192.168.0.1` | 0.403 ms | 0.585 ms | 1.086 ms | 0.149 ms |
| Eclipse **wlan0** `.183` — *the real path* | 1.482 ms | **5.785 ms** | 14.280 ms | 2.651 ms |
| Eclipse eth0 `.182` — via the extender | 2.022 ms | 8.921 ms | 35.737 ms | 6.404 ms |

⚠️ **The stream path pings *better* than the extender path, and still loses 7.1 % of frames.**
Latency and small-packet loss say nothing about whether a link can absorb 60 Hz bursts at
100 Mbps. Do not clear a path on a clean ping.

## ⭐ "The extender dropped to 64 Mbps" — it did not

The dashboard's *Test link* reported **64.3 ↓ / 30.3 ↑** and looked like a collapse from ~300.
Both numbers are artefacts:

1. The test runs over **wlan0** (it is the default route), so it never touched the extender.
2. It ran **while the 101 Mbps game stream was saturating that same radio** — Kodi reads
   `inactive` because Moonlight still owns the box. 64 Mbps is simply what was left.
   64 + 101 ≈ **165 Mbps aggregate**, a normal real-world figure for a 292 Mbit/s PHY at −67 dBm.
3. The familiar "~300" is `wlan0`'s **rx PHY rate of 292.5 Mbit/s** — i.e. the dashboard has been
   measuring the Wi-Fi radio all along. The 196 Mbps baseline in
   `eclipse-extender-bridge-bottleneck` is the **eth0/extender** path. Different paths, different
   numbers; both are right.

**Never read that panel during a stream, and know which interface it measured.**

## Ruled out, with numbers

- **Not Proton.** Proton Experimental **11.0-100**; the game ran the whole time at 59.6 fps.
- **Not the GPU.** 54–74 % busy, **74 W**, sclk 2382 MHz. When Sisyphus is genuinely GPU-bound
  (the Witcher 3 4K test) it sat at 86–100 % and **172 W of a 182 W cap**. Nowhere near it.
- **Not the Pi.** HEVC **V4L2 stateless hardware** decode (`Hwaccel V4L2 HEVC stateless V4`,
  DMABuf in and out), `throttled=0x0`, 59.3 °C, load 1.36 on 4 cores.
- **Not a codec mismatch.** HEVC throughout, which is the one the Pi decodes in hardware.
- **Not the extender.** It carried none of this traffic.

## Fix

1. ⭐ **Drop Moonlight's bitrate from `100000` to `40000`-`50000`.** Observed oversized blocks were
   median 308 / max 622 against the 255 ceiling, so a 0.41–0.83× cut puts essentially every block
   **back under the FEC limit** — frames get parity again — and takes airtime from ~60 % to ~25 %.
   4K60 **HEVC** at 40–50 Mbps is visually ample for a 2D stylised game.
   ⚠️ **Do not hand-edit `Moonlight.conf` while Moonlight is running** — it is a Qt `QSettings`
   file rewritten on exit. Set it from Moonlight's settings screen on the TV, or with it stopped.
2. ⭐ **Pick one interface.** Two NICs on one subnet with Wi-Fi holding the default route is
   non-deterministic, bypasses the extender, and makes every dashboard reading ambiguous.
   Either set `AutoConnect=false` on `Kandy Cane` so the wired path is used, or drop `eth0` and
   accept −67 dBm as the ceiling.
3. **Then re-measure both paths with nothing streaming** and keep the better one. On this
   evidence it is not obvious which wins: wlan0 pings better, eth0 historically moved 196 Mbps.

# RESOLVED, same evening — eth0 wins decisively

After the extender was power-cycled, both paths were measured **idle** (stream ended, Kodi back).
This is the clean comparison the sections above could not make:

| path | throughput | ping (idle, 1400 B) |
|---|---|---|
| `eth0` → RP-BE58 extender | **376 Mbps** (47,044,804 B/s) | **2.17 / 2.99 / 7.03 ms**, mdev 0.96 |
| `wlan0` → router direct, −66 dBm | 158 Mbps (19,703,467 B/s) | 5.79 / 14.3 ms, mdev 2.65 |

**The extender path is 2.4× faster and lower latency.** Its antennas and placement beat the Pi's
internal radio comfortably.

## ⚠️ Two measurement traps that produced the wrong answer earlier

1. **The earlier eth0 ping (8.92 avg / 35.7 max) was taken while `wlan0` was saturated** with the
   101 Mbps stream. Both radios share the same airspace, so the idle interface measured badly
   *because of load on the other one*. With wlan0 down, eth0 measures 2.99 / 7.03.
   **Never compare two wireless paths while one of them is carrying a stream.**
2. ⭐ **Latency did not predict throughput here.** wlan0 pinged better and moved less than half
   the data. A hop count argument ("eth0 adds a hop, so it's worse") was wrong for the same
   reason — the extra hop is on much better radios. **Measure throughput; do not infer it.**

## What was changed

```bash
connmanctl config wifi_88a29ed653de_4b616e64792043616e65_managed_psk --autoconnect off
connmanctl disconnect wifi_88a29ed653de_4b616e64792043616e65_managed_psk
```

Run detached via `systemd-run` so it survives killing its own transport. Result: `Kandy Cane` is
`*` (neither auto nor connected), `AutoConnect=false` is persisted in
`/storage/.cache/connman/<svc>/settings` so it survives a reboot, `wlan0` has no address, and the
single default route is `dev eth0`. Tailscale re-homed onto eth0 without intervention.

## Bitrate — now a second-order question

At 364 Mbps a 101 Mbps stream is **~28 % utilisation**, against ~60 % airtime on wlan0 before.
The 255-packet FEC ceiling is still crossed at `bitrate=100000`, so residual loss remains
unrecoverable — but there should be far less of it.

**Play it at 100000 first.** If it is clean, leave it. If spikes persist, *then* drop to
40000-50000, because at that point the unprotected frames are what is left.
